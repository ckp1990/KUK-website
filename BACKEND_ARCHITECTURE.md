# Backend Architecture & Data Strategy

This document outlines the recommended backend architecture for the Wildlife Science Portfolio website, focusing on a serverless, scalable, and cost-effective solution using Google Firebase.

## Goals

1.  **Decouple Data & Assets:** Separate heavy media files (images, videos) and structured data (testimonials, species info) from the Next.js application code to keep the repository lightweight and performant.
2.  **Enable Dynamic Updates:** Allow content updates (e.g., adding a new testimonial) without requiring a full code deployment.
3.  **Future-Proof for CRM:** Build a foundation that easily integrates with a future Customer Relationship Management (CRM) system.
4.  **Cost-Effective:** Leverage generous free tiers (e.g., Google Firebase Spark Plan) suitable for a portfolio site.

---

## 1. Core Architecture: Google Firebase

We recommend using **Google Firebase** as the backend-as-a-service (BaaS) platform. It provides a robust, developer-friendly ecosystem that integrates seamlessly with Next.js and GitHub Pages.

### A. Data Storage: Cloud Firestore (NoSQL Database)

*   **Purpose:** Store structured content such as:
    *   **Testimonials:** Name, role, quote, image URL.
    *   **Species of Interest:** Name, scientific name, description, image URL.
    *   **Publications:** Title, year, link, category.
    *   **Blog Metadata:** Title, slug, date, tags (if moving away from Markdown files).
*   **Why Firestore?**
    *   **JSON-like Structure:** Fits perfectly with modern JavaScript/TypeScript apps.
    *   **Real-time Updates:** While not strictly needed for a static site, it allows for instant admin previews.
    *   **Scalability:** Automatically scales with your data.
    *   **Free Tier:** 1GB storage, 50k reads/day, 20k writes/day (more than enough for this portfolio).

### B. Asset Storage: Cloud Storage for Firebase

*   **Purpose:** Store high-resolution images, PDFs (publications), and other media files.
*   **Why Cloud Storage?**
    *   **CDN Integration:** Images are served via a global Content Delivery Network (CDN), ensuring fast load times worldwide.
    *   **Direct URLs:** Generates public URLs (e.g., `https://firebasestorage.googleapis.com/...`) that you can directly use in your Firestore documents.
    *   **Security:** granular access controls.
    *   **Free Tier:** 5GB storage, 1GB/day download bandwidth.

### C. Hosting: GitHub Pages (Current)

*   **Role:** Serves the static HTML/CSS/JS bundles generated by Next.js.
*   **Integration:** The build process fetches data from Firestore and images from Cloud Storage *at build time* (using `getStaticProps` or `generateStaticParams`) to produce fast, static pages.

## 2. Integration Workflow

This setup creates a smooth pipeline from content creation to deployment.

1.  **Content Entry:**
    *   *Initial Phase:* You manually add data (JSON) to Firestore and upload images to Storage via the Firebase Console.
    *   *Future CRM Phase:* A custom Admin Panel or CRM connects to Firestore. When you add a testimonial in the CRM, it writes to the Firestore database.

2.  **Build Trigger:**
    *   *Option A (Manual):* You push code to GitHub.
    *   *Option B (Automated):* You can set up a webhook (using Firebase Cloud Functions) to trigger a GitHub Actions workflow whenever data in Firestore changes. This rebuilds your site automatically with the new content!

3.  **Next.js Build:**
    *   During `npm run build`, Next.js queries Firestore for all testimonials, species, etc.
    *   It generates static HTML pages populated with this data.
    *   Images are referenced by their remote Firebase Storage URLs.

4.  **Deployment:**
    *   The generated `out/` directory is deployed to GitHub Pages.

## 3. Preparing for CRM Integration

Since you plan to add a CRM, this architecture is ideal because **Firestore acts as the central source of truth**.

*   **The CRM (Frontend):** This will be a separate, secure interface (or a route like `/admin` in this app) where authenticated users can manage content.
*   **The CRM (Backend):** It will read/write directly to Firestore.
*   **Workflow:**
    1.  Admin logs into CRM.
    2.  Admin uploads a photo -> CRM saves it to **Firebase Storage** and gets a URL.
    3.  Admin adds testimonial text -> CRM saves text + image URL to **Firestore**.
    4.  (Optional) CRM triggers a site rebuild via GitHub API.

This separation ensures your public website remains static and fast, while your management system is dynamic and secure.

## 4. Implementation Steps

### Step 1: Set up Firebase Project
1.  Go to [console.firebase.google.com](https://console.firebase.google.com/).
2.  Create a new project (e.g., `ullas-karanth-portfolio`).
3.  Enable **Cloud Firestore** (start in Test Mode for development).
4.  Enable **Storage**.

### Step 2: Configure Next.js
1.  Install the Firebase SDK: `npm install firebase`.
2.  Create a config file (`lib/firebase.ts`) with your project keys.
3.  Create utility functions to fetch data (e.g., `getTestimonials()`).

### Step 3: Update Components
*   Modify `app/page.tsx` (and others) to use these async functions to fetch data instead of using hardcoded arrays.

### Step 4: Environment Variables
*   Store your Firebase API keys in `.env.local` for local development.
*   Add these keys as **Secrets** in your GitHub Repository settings for the CI/CD pipeline.
